# AI 估算的前端（並讓後端可以在 Anthropic 與 Gemini 之間切換）

**狀態：** 已實作（`feat/ai-estimate`）
**日期：** 2026-10-05
**前置：** P2 後端（`POST /api/ai/analyze`，規格 `2026-09-27-p2-ai-analysis-design.md`）已在 master；修改與刪除餐點已合併（master `99a633b`）

---

## 1. 目標與範圍

### 1.1 為什麼要做

P2 規格把前端也設計了（兩個入口、確認／需要修改、存成食物），但只做了後端——
`POST /api/ai/analyze` 在 master 上，前端沒有任何入口，使用者用不到。

另外有一條沒合併的分支 `feat/p2-gemini`，把 LLM 供應商從 Anthropic **換成** Gemini。
使用者要兩家都能用。

### 1.2 這份規格做的事

1. 後端可以用設定在 Anthropic 與 Gemini 之間切換（部署時選一家）。
2. 估算的回應補兩個欄位（`food_id`、`remaining_today`）；撞名錯誤附上現有食物的 id；
   沒設定 AI 時，文字命中食物庫照樣能用。
3. 前端一個共用的估算面板 `AiEstimatePanel`，放在**記一餐**與**新增食物**兩個地方。
4. 記一餐用「拍照估算」時，那張照片自動當這一餐的照片。

### 1.3 明確不做

- 主要／備援兩家自動切換、使用者在畫面上選供應商（§2）。
- 「編輯這一餐」的「加一項」放 AI——它也用 `FoodPicker`，以後要加只是多傳一個 prop。
- P2 規格 §11 的範圍外項目照舊不做：辨識歷史、圖片保存（估算用的圖片）、多食物辨識、
  補劑辨識、AI 建立全域食物、串流回應。
- 在畫面上顯示 AI 自陳的信心值（P2 規格 §4.1：不可以被當成可靠度顯示）。

## 2. 已經做出的決定

| 決定 | 選項 | 理由 |
|---|---|---|
| 兩家怎麼並存 | **部署時設定一家**（`AI_PROVIDER`） | 最簡單、行為可預測；備援會讓一次估算可能花兩次錢，每日上限也變複雜 |
| 入口放哪裡 | **記一餐與新增食物都放**，共用同一個元件 | 記一餐是最常遇到「食物庫沒有」的地方；新增食物是工具型入口 |
| 拍照估算的照片 | **自動帶入這一餐的照片**（已經選了別張就不覆蓋） | 拍一次就同時有估算與紀錄 |
| 畫面形式 | **內嵌面板**（範例 A：結果出現在搜尋框下面） | 不換頁，記一餐已經填的金額、照片都還在；元件可以單獨測試 |
| 「需要修改」在哪裡改 | **面板自己的修改模式**（兩個入口都是） | 只有一套修改介面；新增食物的表單沒有地方放「AI 原本說了什麼」 |

## 3. 後端

### 3.1 兩家並存，用設定切換

| 環境變數 | 說明 |
|---|---|
| `AI_PROVIDER` | `anthropic` 或 `gemini`。**沒設定＝AI 功能關閉**（`503 AI_NOT_CONFIGURED`，跟現在一樣） |
| `ANTHROPIC_API_KEY` | Anthropic 的金鑰 |
| `GEMINI_API_KEY` | Gemini 的金鑰 |
| `AI_MODEL` | 模型名稱，兩家共用一個變數。**不給預設值** |

- 選定的那一家**沒有金鑰**或**沒有 `AI_MODEL`** → `503 AI_NOT_CONFIGURED`，訊息說明缺哪一個
  （例如「AI 分析未設定：缺 GEMINI_API_KEY」）。
- **不猜模型名稱的預設值**：猜錯的名字要到第一次真的呼叫才失敗，而且錯在更難查的地方
  （`feat/p2-gemini` 分支 `app/config.py` 的註解）。
- `AI_PROVIDER` 是**不認得的值**（打錯字）→ **啟動時就失敗**。這跟「沒設定＝安靜地關閉」
  不同：打錯字是設定錯誤，要大聲說出來。
- 空字串＝沒設定（`docker-compose` 用 `${VAR:-}` 傳選配變數，沿用既有的正規化）。
  三個新變數都要有這個正規化。
- `ai_analyses.model` 記錄實際用的 `AI_MODEL`（既有行為）。

**程式結構：**

- `app/ai/estimator.py`：兩家共用的部分——`NutritionEstimator` Protocol、`RawEstimate`、
  提示詞、`parse_raw_estimate()`。
- Anthropic 實作與 Gemini 實作各一個檔案。Gemini 實作從 `feat/p2-gemini` 搬過來
  （包括它查證過的 `response_schema` 寫法與註解）；**不直接合併那條分支**——它刪掉了 Anthropic。
- `get_estimator()` 依 `AI_PROVIDER` 建對應的實作。測試仍然要能用
  `app.dependency_overrides` 換成假實作（既有測試依賴這件事）。
- 依賴加上 `google-genai`（版本照 `feat/p2-gemini` 的 `pyproject.toml` 與 `requirements-lock.txt`）。

### 3.2 `POST /api/ai/analyze` 的回應多兩個欄位

| 欄位 | 型別 | 說明 |
|---|---|---|
| `food_id` | `int \| null` | 文字估算**命中食物庫**時是那個食物的 id；真的呼叫了 AI 時是 `null` |
| `remaining_today` | `int` | 今天還能呼叫幾次（`AI_DAILY_LIMIT` − 今天 `ai_analyses` 的列數，最小 0）。命中食物庫不扣次數 |

`food_id` 解決一個既有的洞：命中食物庫時回的是那個食物的資料，但前端沒有 id，只能再建一個
同名食物——然後被 `409 FOOD_EXISTS` 擋下。

### 3.3 沒設定 AI 時，命中食物庫照樣能用

現在 `analyze` 用 `Depends(get_estimator)`，FastAPI 在進 handler 之前就解析依賴——
**沒設定 AI 時，連命中食物庫的文字估算也回 503**。

改成：先查食物庫，**真的要呼叫 AI 時才取得實作**（實作方式留給計畫，但測試要能注入假實作）。
這樣沒有金鑰時，文字命中食物庫照樣能用；e2e 也因此測得到這條路（§6.2）。

### 3.4 `409 FOOD_EXISTS` 附上現有食物的 id

`POST /api/foods` 撞名時，錯誤的 `details` 多一個 `food_id`（撞到的那一筆）。

- 撞名檢查的範圍是「同一個擁有者、同名、同品牌」（`app/api/routes/foods.py`），所以附上的
  一定是**你自己的**食物（或管理員建全域食物時撞到的全域食物）——不會洩漏別人的私人食物。
- `IntegrityError` 那條路（並行建立時才會走到）也要附上：rollback 之後重查一次那一筆。

### 3.5 後端測試

- **切換**：`AI_PROVIDER=anthropic`／`gemini` 各自建出對應的實作（斷言實作的型別，不打網路）；
  選定那一家缺金鑰 → 503 且訊息說缺哪一個；缺 `AI_MODEL` → 503；`AI_PROVIDER` 不認得的值 →
  `Settings` 建立失敗；三個新變數的空字串都等於沒設定。
- **`food_id`**：命中食物庫時是那一筆的 id；呼叫 AI 時是 `null`。
- **`remaining_today`**：呼叫一次 AI 減一（失敗的呼叫也減——那一次也花了錢）；命中食物庫不變；
  用完時是 0。
- **沒設定 AI 時命中食物庫**：200，而且**假實作沒有被建立**（不是只斷言結果對——P2 規格 §8.3）。
- **`FOOD_EXISTS` 的 `food_id`**：是撞到的那一筆；別人的同名私人食物**不會**觸發（各自建得起來）。

### 3.6 `schema.d.ts`

重新產生（Windows 上加 `PYTHONUTF8=1 PYTHONIOENCODING=utf-8`）。

## 4. 前端：`AiEstimatePanel`

一個共用元件，放在記一餐與新增食物。它自己處理估算、確認、修改、存成食物，最後把
**一個可以用的食物**（`FoodResponse`）交回給所在的畫面。

### 4.1 流程

1. **輸入**（兩種）：
   - **文字**：由所在的畫面給（記一餐是搜尋框的字，新增食物是面板自己的輸入框）。
   - **照片**：📷 按鈕選一張。先擋大小（`MAX_PHOTO_BYTES`），再 `shrinkToLongestEdge(file, 1280)`，
     轉成 base64 送 `kind: "image"`——跟上傳餐點照片同一套前處理。
2. **估算中**：「AI 估算中…」，按鈕停用。
3. **結果卡片**：
   - 名稱、一份幾 g（或 ml，看 `base_unit`）、一份的熱量與三大營養素（`serving_*`）、
     「今天還能用 N 次」（`remaining_today`）。
   - `consistency.flagged` 時：「⚠ 熱量跟三大營養素對不太起來，建議看一眼」。沒有標記時：
     「✓ 熱量與三大營養素對得起來」。
   - **不顯示 `confidence`。**
4. **確認** → `POST /api/foods`：
   - `name`、`brand`：AI 給的。
   - `nutrition`：回應裡**每 100** 的值（後端算好的，前端不重算——P2 規格 §4.1）。
   - `default_portion`：`{ label: "一份", grams: serving_grams }`。
   - `source: "ai"`、`ai_confidence: confidence`、`ai_raw_response`：整個估算回應。
5. **需要修改** → 卡片變成可編輯：名稱、一份重量、一份的熱量／蛋白質／脂肪／碳水。
   存的時候：
   - `nutrition`：用 `perServingToPer100()`（`lib/decimal.ts`，新增食物「每一份」模式已經在用）
     把每份換算成每 100；上限檢查與錯誤訊息沿用新增食物（換算後超過上限時說「換算後超過上限，請確認一份的重量」——跟面板「一份的…」的用詞一致）。
   - `default_portion`：`{ label: "一份", grams: 改過的一份重量 }`。
   - `source: "user"`、`ai_confidence` 與 `ai_raw_response` **照樣送 AI 原本的**
     （P2 規格 §5：改過之後仍然存 AI 說的，之後才問得出「AI 常常錯很多嗎」）。
   - 「放棄修改」回到結果卡片。

### 4.2 特殊情況

| 情況 | 畫面 |
|---|---|
| 文字命中食物庫（`food_id` 不是 null） | 「食物庫裡已經有『牛肉麵』」＋「用這個」→ `GET /api/foods/{food_id}` → 交回。**不建新食物** |
| 存的時候撞名（`409 FOOD_EXISTS`，有 `details.food_id`） | 「你已經有『牛肉麵』了」＋「用現有的」（同上，取那一筆交回）＋「改名」（打開修改模式） |

### 4.3 錯誤（顯示在面板裡）

| 錯誤 | 訊息 |
|---|---|
| `429 AI_DAILY_LIMIT` | 後端的訊息（含「今天用了 N/20」） |
| `503 AI_NOT_CONFIGURED` | 「AI 分析未設定」；面板的估算按鈕停用（這一次畫面上的） |
| `502 AI_BAD_RESPONSE` | 「AI 這次的回答看不懂，可以再試一次」（這一次也算在今天的次數裡） |
| `PHOTO_TOO_LARGE`／`INVALID_PHOTO`／前端擋下的太大 | 沿用 `describePhotoUploadError()` |
| 存食物失敗（其他） | 「存成食物失敗，請再試一次」；`VALIDATION_ERROR` 用 `describeFieldErrors` |
| 其他 | 「AI 估算失敗，請再試一次」 |

### 4.4 資料流

- 存成食物之後失效食物搜尋（`["food-search"]` 前綴），新食物在食物庫與下次搜尋就看得到。
- 常吃／最近吃要等真的記了一餐才會變——由記一餐既有的失效處理。
- 估算本身**不快取**（每一次都是一次呼叫、一次扣次數；用 mutation，不用 query）。

## 5. 兩個入口

### 5.1 記一餐（`LogMeal`）

- `FoodPicker` 多一個**選填**的 prop（例如 `aiEntry`）。有給的時候：
  - 搜尋框旁邊一個 📷 按鈕（拍照估算）。
  - **搜尋框有字時**，搜尋結果下面出現「用 AI 估算『{字}』」——不只在完全找不到時出現
    （搜尋結果可能只是部分相符）。
  - 編輯這一餐的「加一項」不給這個 prop，所以沒有 AI。
- 面板顯示在搜尋區下面（範例 A）。
- 面板交回食物 → **選上它**；份量自動是「一份 × 1」（剛建的預設份量；`usePortionQuantity`
  既有的「自己的預設份量優先」規則），接著照常填餐別、金額，按「記錄」。
- **照片帶入**：拍照估算用的那張照片，在**記一餐還沒有選照片時**自動放進「照片（選填）」
  （可以按「移除照片」拿掉）；已經選了別張就不覆蓋。放進去的是**原始檔案**（記一餐上傳時
  自己會縮），面板只負責回報「用了哪張」。
- 命中食物庫或「用現有的」交回的食物，一樣選上；它可能沒有「一份」，就照既有規則（有預設份量
  用預設、沒有就直接輸入數量）。

### 5.2 新增食物（`NewFood`）

- 表單上方一個「用 AI 填」區塊：文字輸入框＋「估算」＋📷。
- 面板交回食物 → 導到 `/foods/{id}`（跟手動建立成功一樣）。
- 手動填表單的路照舊，不受影響。

## 6. 測試

### 6.1 前端單元／元件

`AiEstimatePanel`（API 一律 mock）：

- 文字與照片兩條路送出的 body（照片要先經過 `shrinkToLongestEdge`——mock 它）。
- **確認**：`POST /api/foods` 的 body——每 100 的值、`default_portion`、`source: "ai"`、
  `ai_confidence`、`ai_raw_response`。
- **需要修改**：換算後的每 100、改過的一份重量、`source: "user"`、AI 原本的 `ai_raw_response`。
- 命中食物庫：**沒有送 `POST /api/foods`**，交回的是 `GET /api/foods/{id}` 那一筆。
- 撞名：「用現有的」交回那一筆；「改名」打開修改模式。
- 每一種錯誤的訊息；503 之後估算按鈕停用。
- 一致性標記的兩種文字。
- **畫面上找不到 `confidence` 的值**（有一條測試專門守——用一個不會跟其他數字撞的值，例如 `0.37`）。

記一餐：確認後選上食物、份量選項是「一份」、數量 1；照片自動帶入；**已經選了照片時不覆蓋**。
新增食物：交回後導到詳情頁。

`log-meal.test.tsx` 既有的測試不應該需要改（`aiEntry` 是新的選填 prop）。

### 6.2 e2e

CI 沒有 AI 金鑰，而且 e2e 不該花錢——只走不需要 AI 的路：

1. 記一餐：用 AI 估算一個**食物庫裡已經有**的名稱（測試自己先建一個唯一名稱的食物）→
   「食物庫裡已經有」→「用這個」→ 記錄 → 飲食頁看到那個食物。
2. 用 AI 估算一個**不存在**的名稱 → 「AI 分析未設定」。

真的呼叫 AI 的路由元件測試與後端測試（假實作）守著。
