# 食物的「一份」——新增食物時設定份量、照營養標示輸入

**狀態：** 設計定稿，待寫實作計畫
**日期：** 2026-10-03
**前置：** 介面改版第一階段已上線（master `6296685`）

---

## 1. 目標與範圍

### 1.1 為什麼要做

使用者原話：「新增食物應該有一份單位」。

現況（handover §8.2 已記錄的缺口）：份量的後端（`food_portions`、`POST /api/foods/{id}/portions`）從 P1 就有，**前端沒有任何新增份量的介面**。記一餐因此只能打公克數，打不出「一碗」。營養素也只能用「每 100 g」輸入，而台灣的包裝營養標示通常寫「每一份量 45 公克」。

另外，正式環境的食物庫目前是空的——接下來使用者會自己建很多食物，所以「新增食物」這個表單好不好用是第一優先。

### 1.2 這份規格做的事

1. 新增食物時可以選填「一份」（名稱＋重量），**跟食物在同一個交易裡建立**。
2. 新增食物時營養素可以用「每 100 g」或「每一份」輸入；「每一份」在前端換算成每 100 g 再送。
3. 食物詳情頁可以替任何看得到的食物新增**自己的**份量。
4. 記一餐選了食物之後，有預設份量就直接選好它（數量 1）。

### 1.3 明確不做

- 刪除或修改份量（後端沒有端點）
- 在食物詳情頁「提議修改營養素」時用「每一份」輸入（只有新增食物有）
- 管理員在介面上建立公開食物或公開份量（`/foods/new` 仍然只建私人食物）
- 一個食物一次建多個份量（新增時只有一個；之後到詳情頁加）

## 2. 已經做出的決定

| 決定 | 選項 | 理由 |
|---|---|---|
| 要解決哪種情況 | **兩種都要**：記一餐選「1 碗」、照包裝標示的「每份」輸入 | 使用者選 C |
| 已存在的食物能不能加份量 | **能**，在食物詳情頁 | 使用者選 B；只做新增食物的話，公開食物永遠只能打公克 |
| 食物與份量怎麼建立 | **後端一次建立**（同一個交易） | 使用者選 A；不會留下「食物建了、份量沒建」的半套狀態——跟記一餐帶餐費同一種作法 |
| 營養素存什麼 | **一律每 100 單位**，「每份」在前端換算 | 後端不變；換算經過 `lib/decimal.ts`，不經過浮點 |

## 3. 後端

### 3.1 `POST /api/foods` 多一個選填欄位

```json
{
  "name": "滷肉飯",
  "nutrition": { "base_unit": "g", "kcal": "180.00", "...": "..." },
  "default_portion": { "label": "碗", "grams": "150" }
}
```

- 新 schema：`DefaultPortionInput`，`label: str = Field(min_length=1, max_length=50)`、`grams: Decimal = Field(gt=0, le=10000, max_digits=8, decimal_places=2)`——**跟 `PortionCreateRequest` 的同名欄位同一組限制**。
- `FoodCreateRequest.default_portion: DefaultPortionInput | None = None`。
- 有帶時，在 `create_food` 裡、**`commit` 之前**加一筆 `FoodPortion`：
  - `food_id` = 新食物
  - `owner_id` = 跟食物一樣（私人食物 → 使用者；公開食物 → `None`）
  - `label`、`grams` 照送進來的
  - `is_default = True`
- 不帶時行為完全不變。
- 回應 `FoodResponse` 不變（不內嵌份量；前端建立後導到詳情頁，那一頁本來就抓份量清單）。

### 3.2 後端測試（`tests/` 裡食物相關的測試檔）

1. 帶份量：份量建立、`is_default` 為真、名稱與重量正確、`GET /api/foods/{id}/portions` 看得到。
2. 不帶份量：沒有份量（既有測試照常綠）。
3. 份量格式錯誤（`grams: "0"`）→ 422，**而且食物沒有被建立**（守「同一個交易」）。
4. 管理員建立公開食物並帶份量 → 份量是公開的（`is_global` 為真）；一般使用者建立私人食物 → 別的使用者看不到那個份量。

### 3.3 `schema.d.ts`

重新產生。**在 Windows 上要加 `PYTHONUTF8=1 PYTHONIOENCODING=utf-8`**——介面改版第一階段 Task 1 實測：不加的話 docstring 的中文會被編碼弄壞，`openapi-typescript` 直接當掉。

## 4. 新增食物畫面（`frontend/src/screens/NewFood.tsx`）

### 4.1 表單

由上而下：

1. 名稱、品牌（選填）、單位（g / ml）——不變。
2. **「一份（選填）」**：
   - 份量名稱（例如：碗、片、包）
   - 每份重量（單位跟著上面的 g / ml）
   - **兩個要一起填**；只填一個 → 「份量名稱與重量要一起填」。
3. **「營養標示是」**二選一：「每 100 g」（預設）／「每一份」。
   - 每份重量沒填（或不是正數）時「每一份」不能選，旁邊寫「先填每份的重量」。
   - 已經選了「每一份」之後又把重量清掉 → 自動切回「每 100 g」（不能停在一個無法換算的狀態）。
4. 營養素四個欄位：
   - 「每 100 g」模式：**標籤跟現在一字不差**（例如「熱量（每 100 單位 kcal）」）。`e2e/foods.spec.ts`、`e2e/admin.spec.ts`、`e2e/mobile-form-zoom.spec.ts` 都用這些標籤找欄位，而且 `FoodDetail` 共用同一組定義（`NUMERIC_FIELDS`）。
   - 「每一份」模式：標籤改成「熱量（每份 kcal）」、「蛋白質（每份 g）」等。
   - **只有 `NewFood` 的標籤會切換**；`FoodDetail` 的提議修改維持每 100。

### 4.2 「每一份」的換算

`frontend/src/lib/decimal.ts` 新增純函式：

```ts
perServingToPer100(value: string, servingGrams: string): string | null
```

- 結果 = `value × 100 ÷ servingGrams`，**四捨五入到小數兩位**（`Decimal.ROUND_HALF_UP`），回字串。
- `value` 或 `servingGrams` 不是合法數字、或 `servingGrams` 不是正數 → 回 `null`（**不丟例外、不除以零**）。

畫面上**即時顯示換算結果**：「換算成每 100 g：熱量 466.67 kcal、蛋白質 …」。使用者送出前就看得到實際會存什麼。

**上限檢查用換算後的值**（既有的 kcal ≤ 10000、其他 ≤ 1000）。超過時訊息是「換算後超過上限，請確認每份重量」——通常代表重量少打一位數。

> 精度說明：每 100 存兩位小數，記一餐用「1 份」時會再乘回去。例如每份 45 g、210 kcal → 存 466.67 → 記一份算出 210.0015，顯示 210。誤差在第三位小數以下，可以接受，**但要在換算函式的 docstring 寫明**。

### 4.3 送出

- `nutrition`：每 100 g 的值（「每一份」模式送換算後的）。
- `default_portion`：有填份量就帶 `{ label, grams }`（`label` trim）。
- 成功 → 照現在導到 `/foods/{id}`。
- 錯誤處理不變：`FOOD_EXISTS`、`VALIDATION_ERROR`（`describeFieldErrors`）、其他。

## 5. 食物詳情頁（`frontend/src/screens/FoodDetail.tsx`）

「份量」區塊在清單下面加一個表單：

- 欄位：份量名稱、重量（單位跟著食物）、勾選框「記一餐時預設用這個份量」。
- 勾選框的初始值：**這個食物目前沒有任何預設份量時勾起來**，有的話不勾。
- 送出 `POST /api/foods/{id}/portions`，`is_global` 一律 `false`（私人份量）。
- 成功 → 失效 `queryKeys.portions(foodId)`，表單清空。
- 錯誤：
  - `409 PORTION_EXISTS` → 後端的訊息「你已經為這個食物建過同名的份量了」。
  - `422 VALIDATION_ERROR` → 欄位錯誤（`describeFieldErrors`）。
  - 其他 → 「新增份量失敗，請再試一次」。
- 送出中按鈕停用。

順手修：清單的「（150 g）」改成跟著食物的單位（液體顯示 ml）。

## 6. 記一餐（`frontend/src/screens/LogMeal.tsx`）

- 選了食物、份量清單載入之後，**如果有預設份量就預先選它**，數量是 1。
  - 挑選順序：自己的預設份量（`is_default && !is_global`）優先，沒有才用公開的預設份量（`is_default && is_global`）。
  - 使用者仍然可以改成「直接輸入數量」或其他份量；**一旦使用者手動選過，就不再自動覆蓋**。
- 數量欄的標籤維持「份量」（`e2e/trend.spec.ts` 用 `getByLabel("份量")`）。旁邊加單位提示：選了份量時「份」，直接輸入時「g」或「ml」。
- 選了預設份量時，數量的初始值是 `"1"`——現在的初始值本來就是 `"1"`，所以不用改；但**直接輸入模式下的 `"1"` 代表 1 g**，單位提示讓這件事看得出來。

實作提示（不是限制）：用「使用者是否手動選過」的狀態加上從份量清單推導出的預設，避免用 effect 在資料到的時候寫 state。

## 7. 測試

### 7.1 單元與元件

- `perServingToPer100`：一般換算、四捨五入（例如 210 / 45 g → "466.67"）、重量 0 / 空 / 非數字 → `null`。
- `NewFood`：
  1. 帶份量送出：body 的 `default_portion` 正確。
  2. 「每一份」模式：送出的 `nutrition` 是換算後的值。
  3. 只填份量名稱或只填重量 → 擋下、不送請求。
  4. 沒填每份重量時「每一份」不能選。
  5. 換算後超過上限 → 擋下並顯示訊息。
  6. **「每 100 g」模式下四個欄位的標籤跟現在一字不差**（守既有 e2e）。
- `FoodDetail`：新增份量成功（清單重抓）、409 訊息、預設勾選框的初始值規則、液體顯示 ml。
- `LogMeal`：
  1. 有自己的預設份量 → 自動選上，送出帶它的 `portion_id`、`quantity: "1"`。
  2. 只有公開的預設份量 → 選公開的。
  3. 兩者都有 → 選自己的。
  4. 沒有預設份量 → 維持「直接輸入數量」。
  5. 使用者手動改成「直接輸入數量」之後不會被改回去。

每條關鍵防線做突變檢查。

### 7.2 e2e

新增一條：新增食物時填「一份 = 碗 150 g」→ 記一餐選這個食物 → 份量選項已經是「碗」→ 記錄 → 飲食頁的熱量是「每 100 g × 1.5」。打真的後端。

既有 e2e 不應該需要改（標籤都沒變）；如果需要，代表某個標籤被改到了。
