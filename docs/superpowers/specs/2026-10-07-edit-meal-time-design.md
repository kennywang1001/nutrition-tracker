# 編輯這一餐可以改時間

**狀態：** 已實作
**日期：** 2026-10-07
**前置：** 照片縮圖已合併（master `6e25664`）

---

## 1. 目標與範圍

記錯時間現在只能刪掉重記（handover §8.2「不能改時間」）。後端 `PATCH /api/meals/{id}` 早就收 `eaten_at`，
但**既有餐費的 `spent_at` 不跟著動**——把上個月補記的晚餐改回上個月，錢還留在這個月的報表。
前端「編輯這一餐」沒有時間欄位。

**不做：** 後端擋未來的時間（前端擋；既有 API 測試會用各種時間）；改餐費自己的日期（報表只能改金額，
一餐的餐費日期一律等於吃的時間）。

## 2. 已經做出的決定

| 決定 | 選項 | 理由 |
|---|---|---|
| 餐費的日期 | **一律跟著吃的時間** | 報表不能單獨改餐費日期；錢屬於吃那一餐的時間（P5 規格 §4.1） |
| 輸入方式 | **日期與時間兩格**（使用者選 A） | 手機原生選擇器；最常見的「改成昨天」只動日期 |
| 時區 | **這台裝置的時區** | 輸入框顯示的就是手機時鐘的時間；「算哪一天」照舊由後端依帳號時區決定 |

## 3. 後端

`update_meal`：`eaten_at` 在這次的改動裡、而且這一餐有餐費（`_existing_meal_expense`）→ 同一個交易裡
`existing.spent_at = meal.eaten_at`。同一次「改時間＋補金額」→ 新建的餐費本來就用 `meal.eaten_at`
（setattr 在前）——加測試釘住。docstring 裡「既有餐費的 `spent_at` 不跟著動」的已知落差拿掉。

## 4. 前端

`EditMeal.tsx` 的 `MealDetailsForm`：

- 「日期」（`type="date"`、`max`＝今天）與「時間」（`type="time"`），預填這一餐在裝置時區的日期與時間（分鐘）。
- 草稿同其他欄位（`undefined`＝沒動）。**只有「日期 時間」字串（到分鐘）跟原本不同才送 `eaten_at`**——
  不會因為原本的秒數就被當成有改。送的是 `new Date("YYYY-MM-DDTHH:mm")`（裝置時區）的 ISO 字串。
- 組起來的時間比現在晚 →「不能選未來的時間」（`role="alert"`），「儲存」disabled。
- 存好之後（有送 `eaten_at` 時）額外失效：`queryKeys.dailyStats`、`queryKeys.rangeStatsAll`、`queryKeys.expensesAll`
  （一餐換了日子，今天的統計、趨勢、支出都會變；`meals` 原本就失效）。

## 5. 測試

- 後端：改時間 → 餐費 `spent_at` 跟著改（rollback 後查）；跨月 → `GET /api/expenses?month=` 舊月沒有、新月有；
  沒有餐費照常；改時間＋補金額 → 新餐費用新時間。
- 前端：預填；只改日期 → 送出的 `eaten_at` 換成新日期、時間不變；沒改 → body 沒有 `eaten_at`；
  未來 → 訊息、不能存、沒有 PATCH；存好之後失效那三個 key（未掛載的 query 不會重抓，用既有的
  `invalidateQueries` spy 寫法）。
