# P2 — AI 從文字與圖片估算一份的營養素

- 日期：2026-09-27
- 階段：P2（原本排在 P3 之前，實際上最後做）
- 狀態：待審

---

## 1. 目標與範圍

### 1.1 這份規格是在前提**已經成立**的情況下寫的

P3-A 規格 §1.1 說過「趨勢圖要看什麼、食物庫要怎麼找，這些問題在累積了兩週
真實資料之後才有答案」，而 P3-B 與 P3-C 都是在那個前提**沒有**成立的情況下
做完的。

**這一份不一樣。** P3 於 2026-09-26 第一次部署到 NAS 並被真的用，而這份規格的
每一個形狀決定都來自使用者用過之後的回答，不是推導：

| 問題 | 使用者的答案 |
|---|---|
| 驗證步驟長什麼樣 | 「顯示估算值按確認　有需要改 再留一個按鈕 點進去改　**代表自己也不確定**」 |
| 文字跟圖片幾個入口 | 「兩個」 |
| 費用 | 「設每日上限　同樣輸入 可以點之前的」 |
| 辨識結果要不要存成食物 | 「辨識出來的東西存成食物」 |

**「代表自己也不確定」這句話改變了資料模型**（見 §5）：它把「有沒有改」從
一個操作變成一筆資料。

### 1.2 P1 已經替 P2 做好的事

P1 規格 §11 就設計了 pipeline 並**預留了欄位**。實測確認那三個欄位從第一版
migration 就在資料庫裡，還帶著約束：

```
source          text NOT NULL DEFAULT 'user'   -- 'user' | 'ai' | 'official'
ai_confidence   numeric(3,2)                   -- CHECK (IS NULL OR 0 <= x <= 1)
ai_raw_response jsonb
```

`app/api/routes/foods.py` 的 `create_food` **完全沒有碰過它們** —— 從 P1 到
現在一直是預設值。P2 是第一個使用者。

> P1 規格對這個決定的說明值得留著：「判斷標準是『事後補的代價』…
> **哪些決定要提早做、哪些可以延後 —— 這個判斷本身就是設計能力。**」
> 這次證明了它是對的：省掉一次要動既有資料、回填、改所有查詢的變更。

### 1.3 範圍

- `POST /api/ai/analyze`：文字或圖片 → 一份的營養素估算 + 驗證結果。**不落庫。**
- 每日呼叫上限（20 次），以及記錄每一次呼叫的資料表
- 純函式的營養素一致性驗證
- 前端：兩個入口（文字／圖片）、估算結果的確認與修改、存成食物

### 1.4 範圍外

- **辨識歷史的畫面**。使用者選了「先搬自己的食物庫，找不到才問 AI」——
  食物庫本身就是快取，確認過的結果會存成食物，所以用越久呼叫越少。
- **圖片保存**。送去辨識完就丟，見 §6。
- **多食物辨識**（一張照片裡有三樣菜）。P1 規格 §11 設想過，但這一版一次
  一樣東西。理由見 §9。
- **全域食物**。AI 存出來的是你的私人食物。
- 補劑的 AI 辨識。

## 2. 為什麼「驗證 agent」改成純函式

P1 規格 §11 把驗證設計成 pipeline 的第 ④ 步，是一個 LLM agent：

> ④ 驗證 agent（熱量 ≈ 蛋白質×4 + 碳水×4 + 脂肪×9？份量合理嗎？）
> ④ 是這個作品集最有價值的部分：展示「我知道 LLM 會胡說，所以我設計了驗證層」

**它要檢查的是算術。** 用 LLM 檢查算術，等於用一個會胡說的東西檢查另一個會
胡說的東西 —— 而且貴、慢、不可重現、測試只能 mock 它。

改成純函式之後：確定性、零成本、測得密、突變得了。

**而規格想展示的那句話在純函式版本反而更成立** —— 因為驗證層本身不會胡說。

### 2.1 驗證規則

```
atwater = 4×protein_g + 4×carb_g + 9×fat_g
偏差    = |kcal − atwater|
標記條件：偏差 > max(kcal × 0.25, 20)
```

**兩個門檻取大的，不是只看百分比。** 低熱量的東西（青菜、零卡飲料）小小的
絕對差就會變成很大的百分比 —— 5 kcal 對 8 kcal 是 60% 偏差，但那沒有意義。
20 kcal 的絕對下限把那類雜訊濾掉。

**25% 這個數字是刻意寬鬆的。** Atwater 係數是近似值，酒精（7 kcal/g）與
膳食纖維都會讓它偏。門檻太嚴會讓每一筆都被標記，而**每一筆都被標記等於沒有
標記**。

### 2.2 標記不擋人

驗證失敗**不阻止**你記錄。AI 可能是對的而係數是近似的；硬擋會讓你記不了東西。

標記的作用是告訴你「這組數字值得看一眼」—— 而那正好餵給 §5 的「需要修改」。

## 3. 流程

```
使用者輸入（文字 或 圖片）
      │
      ├─① 先搜自己的食物庫（DB 查詢，不呼叫 LLM）
      │     找到 → 直接選，結束。**不計入每日上限**
      │     找不到 ↓
      │
      ├─② 檢查今日額度（數 ai_analyses 今天的列數）
      │     超過 → 429，告訴你今天用了幾次、上限幾次
      │
      ├─③ 呼叫 LLM。**不管成功失敗都寫一列 ai_analyses** —— 兩種都花了錢
      │
      ├─④ 純函式驗證（§2）
      │
      └─⑤ 回傳估算值 + 驗證結果 + analysis_id。**到這裡為止沒有寫入任何食物**
            │
            ├─「確認」    → POST /api/foods，source='ai'
            └─「需要修改」 → 編輯後 POST /api/foods，source='user'
                              兩者的 ai_raw_response 都存 LLM 的原始回覆
```

**① 是省錢與準確度的關鍵**（P1 規格 §11 的原話：「能用 DB 解決的就別呼叫
LLM」）。而它會隨使用自動變強：你確認過的每一個 AI 結果都會進食物庫，
下次同一樣東西就走 ① 不走 ③。

## 4. 分析與落庫是兩個端點，這是刻意的

```
POST /api/ai/analyze   → 只回答「AI 說了什麼」。除了額度以外不改變任何狀態
POST /api/foods        → 「你接受了什麼」。既有端點，加三個欄位
```

**分開的理由不是 REST 潔癖，是可稽核性。** AI 說的與你接受的在時間上、在
程式碼上、在資料上都是分開的 —— 所以「AI 常常錯很多嗎、錯在哪一類食物」
之後問得出來（§5）。

合成一個端點的話，「使用者沒接受的那些估算」就完全不存在了，而那正是評估
AI 表現最重要的樣本。

### 4.1 `POST /api/ai/analyze`

Request：

```
{ "kind": "text",  "text": "一碗滷肉飯" }
{ "kind": "image", "image_base64": "..." }
```

Response：

```
{
  "analysis_id": 123,
  "name": "滷肉飯",
  "brand": null,
  "nutrition": {
    "base_unit": "g",
    "serving_grams": "250.00",      ← AI 估的「一份」是幾克
    "kcal": "480.00",
    "protein_g": "14.00",
    "fat_g": "18.00",
    "carb_g": "62.00"
  },
  "confidence": "0.70",
  "consistency": {
    "atwater_kcal": "466.00",
    "deviation": "14.00",
    "flagged": false
  }
}
```

**所有數值都是字串**（跟整個 API 一致，規格 P3-A §5.1）。

> **⚠️ `confidence` 是模型自己說的，不是量出來的。**
>
> LLM 自陳的信心值是出了名的校準不良 —— 它可能對一個完全編造的數字回
> `0.9`。`ai_confidence` 這個欄位是 P1 預留的，存下來沒問題（之後可以拿
> 真實修改率去檢驗它到底準不準），**但它不可以被當成可靠度顯示給使用者**。
>
> 畫面上該顯示的是 §2.1 那個**算得出來**的一致性檢查結果，不是這個自陳值。
> 兩者都叫「信心」會讓人把一個可驗證的訊號跟一個不可驗證的混為一談。
>
> 反過來說，把它存下來正好讓「模型說它有信心的時候，你實際上改了幾次」
> 變成一個查得出來的問題 —— 那才是這個欄位真正的價值。

> **`serving_grams` 是新的概念，要想清楚。** 既有的 `NutritionInput` 是
> **每 100g/ml** 的數值，而 AI 估的是「一份」。兩者要換算，而換算在哪裡做
> 是實作計畫要決定的事 —— **但它一定要在後端做一次、前端不重算**，
> 否則就是第二個事實來源。

錯誤：

| 狀況 | 回應 |
|---|---|
| 今日額度用完 | `429 AI_DAILY_LIMIT` — 訊息要含「今天用了 N/20」 |
| 沒設 `ANTHROPIC_API_KEY` | `503 AI_NOT_CONFIGURED`「AI 分析未設定」 |
| LLM 回傳無法解析的東西 | `502 AI_BAD_RESPONSE` |
| 圖片太大／不是圖片 | 沿用照片上傳既有的 `PHOTO_TOO_LARGE` / `INVALID_PHOTO` 慣例 |

## 5. 「有沒有改」是資料，不只是操作

使用者原話：

> 顯示估算值按確認　有需要改 再留一個按鈕 點進去改　**代表自己也不確定**

那句話的意思是：**編輯這個動作本身帶著資訊**。所以：

| 路徑 | `source` | `ai_confidence` | `ai_raw_response` |
|---|---|---|---|
| 直接按「確認」 | `'ai'` | AI 給的 | LLM 原始回覆 |
| 「需要修改」後確認 | `'user'` | AI 給的 | **LLM 原始回覆（仍然存）** |

**改過之後仍然存 AI 原本的數字**，這是關鍵。它讓你之後回答得出一個很有用的
問題：**「AI 常常錯很多嗎？錯在哪一類食物？」** —— 因為你手上同時有「它說的」
與「你改成的」。

> 這件事**不會因為功能正常運作而自動被驗到**。兩條路徑都會成功存出一個食物，
> 畫面上看起來一模一樣。只有一條專門斷言 `source` 的測試守得住它（§8）。

## 6. 圖片不存

送去辨識完就丟，不寫進 `photo_dir`、不進資料庫。

理由：

1. **沒有回頭看的需求。** 使用者選了「先搬食物庫」而不是「翻辨識歷史」，
   所以不需要重看當初那張圖。
2. **不存就沒有隱私與磁碟的問題。** 存了就要處理保存期限、孤兒清理、
   備份範圍 —— 都是為了一個沒有人要的功能。

**記一餐既有的照片功能不變**（那是「這一餐長這樣」的紀錄，跟辨識是兩件事）。

`ai_analyses` 只存一個 `input_hash`（文字的雜湊或圖片位元組的雜湊），
用途是**觀察重複率**，不是拿來還原輸入。

## 7. 每日上限

**20 次／天，只算真的呼叫 LLM 的次數。**

- 走 ① 從食物庫找到的**不計入** —— 那沒有呼叫 API
- **失敗的呼叫計入** —— LLM 回了垃圾一樣要付錢

### 7.1 為什麼不重用 `app/ratelimit.py`

既有的限速器是**記憶體計數、重啟歸零**（handover §8.2 已記：「單容器記憶體，
重啟歸零。這個規模可接受」）。

對「防濫用」可接受，**對花錢不行** —— 每次部署、每次 NAS 重開都會把上限清掉。
而這個 app 的部署頻率不低。

### 7.2 額度從 `ai_analyses` 數，不另設計數器

```sql
SELECT count(*) FROM ai_analyses
WHERE user_id = :me AND created_at >= :today_start
```

**計數器與實際紀錄不可能對不上，因為它們是同一份資料。**
`:today_start` 用 `day_bounds(today_in_timezone(user.timezone))` —— 跟
`stats/daily`、`meals`、`supplements/today` 同一個「今天」（P1 陷阱 1）。

### 7.3 `ai_analyses` 資料表

```sql
CREATE TABLE ai_analyses (
  id          bigserial PRIMARY KEY,
  user_id     bigint NOT NULL REFERENCES users(id),
  kind        text   NOT NULL,        -- 'text' | 'image'
  model       text   NOT NULL,        -- 實際用的模型 id
  input_hash  text   NOT NULL,        -- 觀察重複率用，不還原輸入
  succeeded   boolean NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

它同時是「這個月花了多少」的唯一依據。

## 8. 測試

### 8.1 LLM 一律 mock

真的呼叫 API 的測試會慢、會花錢、而且**不可重現** —— 同樣的輸入下次回來的
數字可能不同，那種測試綠不綠跟程式碼對不對無關。

### 8.2 真正要測的是不需要 LLM 的那些

| 測什麼 | 為什麼它重要 |
|---|---|
| §2.1 的驗證函式 | 純算術，測得密、突變得了。**包含 20 kcal 絕對下限那條** —— 只測百分比的話，低熱量食物那個雜訊來源沒被守到 |
| 第 21 次被擋 | 而且要驗**失敗的呼叫也計入** |
| **①「搜得到就不呼叫 LLM」** | **要斷言 LLM client 一次都沒被呼叫**，不是斷言結果對。結果對可能只是因為 mock 剛好回一樣的東西 |
| LLM 回傳垃圾 | 缺欄位、負數、超出範圍、不是 JSON —— 都不能讓畫面炸掉 |
| **`source` 在兩條路徑上真的不同** | §5：兩條路徑都會成功，畫面看起來一樣。只有這條守得住 |
| 沒設 API key 時整個功能關閉 | 而且要是「明講原因」，不是壞掉的樣子 |

### 8.3 這一版新增的「綠燈說謊」候選

**「搜得到就不呼叫 LLM」這條，斷言結果是沒有鑑別力的。** 如果測試只斷言
「回傳的營養素等於食物庫裡那筆」，那麼一個**先呼叫 LLM、再用食物庫的值覆蓋**
的實作也會全綠 —— 而它每次都在花錢。

必須斷言的是「那個 client 的方法被呼叫了 0 次」。

## 9. 一次一樣東西，不做多食物辨識

P1 規格 §11 設想過「一張照片吐出一組食物」，資料模型也是為此設計的
（`meal_items` 是一對多）。**這一版不做。**

理由不是技術，是**驗證流程會失控**：三樣食物就要確認三組數字，而每一組都
可能要改。§5 那個「確認 / 需要修改」的設計在一樣東西上很乾淨，在三樣上會
變成一個表格編輯器。

而且份量分配（照片裡那盤菜有多少是飯、多少是肉）是 AI 最容易錯的地方，
錯了之後三組數字全部要重來。

**一次一樣，確認完再拍下一樣** —— 慢一點，但每一步都看得懂。累積幾週真實
使用之後再回來看要不要做多食物，那時會有依據。

## 10. 實作大概會切成兩份計畫

這份規格的量比 P3-B 的任一份計畫大：

- **後端**：`ai_analyses` 資料表與 migration、`POST /api/ai/analyze`、
  LLM client、驗證函式、額度檢查、`create_food` 加三個欄位
- **前端**：兩個入口、估算結果的呈現、確認／修改兩條路徑、一致性標記的顯示

**切法留給寫計畫時決定**，但後端先做是明顯的 —— 前端需要一個真的能打的端點
才寫得出有意義的 E2E，而 mock 一個還不存在的 API 形狀正是這個專案踩過的
那種「兩處講同一件事然後漂移」。

## 11. 不做

| 項目 | 為什麼 |
|---|---|
| 辨識歷史畫面 | 使用者選了「搬食物庫」；食物庫本身就是快取 |
| 圖片保存 | §6 |
| 多食物辨識 | §9 |
| 補劑的 AI 辨識 | 補劑的營養素通常印在罐子上，手打比拍照快 |
| AI 建立全域食物 | 存出來的是私人食物。全域食物要管理員審核（P3-B），而 AI 的估算值不該自動進共用食物庫 |
| 串流回應 | 一次估算幾秒鐘，串流的複雜度換不到什麼 |
